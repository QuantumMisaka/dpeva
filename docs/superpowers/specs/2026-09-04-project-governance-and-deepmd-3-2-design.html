1. 执行摘要

DP-EVA 已具备训练、推理、特征、采集、标注、分析、清洗和探索等独立工作流，也拥有 2D-UQ、DIRECT/2-DIRECT、LLPR、ABACUS 标注、Slurm array、DPA4/DPA4C descriptor 等较丰富的科学与工程能力。但当前仓库的可信边界仍停留在“独立工作流工具箱”：作业成功语义、跨迭代数据谱系、模型产物身份、环境能力、候选评估卡和发布证据没有形成统一闭环。

本设计选择能力驱动、契约优先的渐进式治理：不重写现有科学算法，不把 DP-EVA 扩张为包办一切的训练实验平台，而是在现有 workflow 层之下建立 Reliable Scientific Run Contract，在外部依赖边界建立 DeepMD Compatibility Lane，并用分层验证把软件行为、SAI 运行和科研结论连接起来。

核心裁决：DP-EVA 的下一阶段主线不是新增更多算法，而是把“失败语义 + run manifest + dataset lineage + model artifact identity + eval-card + DeepMD capability matrix”固化为可靠科研运行内核。

产品边界：DP-EVA 负责主动数据与候选证据；FT2DP 工作区负责模型训练和系统评估实验矩阵；下游费托模拟工作区以吸附能、NEB、MD 等应用任务裁决最终模型。

本 SPEC 是本地唯一规范源。当前批准仅授权生成 writing-plans；在实施计划获得显式批准前，不授权代码实施、环境升级、SAI 作业提交、发布或远程镜像。

2. 事实背景与问题定义

2.1 已验证的软件状态

  • 单元测试与覆盖率门禁总体健康，但 integration suite 当前并非全绿，完整集成测试也未进入常规 CI。
  • 默认 Local/Slurm 脚本缺少 fail-closed shell 语义，末尾无条件 completion marker 可掩盖上游命令失败；本地多进程训练未聚合子进程退出码。
  • 基础 Pydantic 配置允许额外字段静默忽略，与项目“Errors Should Never Pass Silently”原则冲突。
  • 输出目录存在覆盖式重建路径，尚无统一 run identity、不可变产物约定或显式 resume/force 语义。
  • 文档治理体系已建立，但路线图、环境文档、traceability matrix 和真实实现之间存在漂移。

2.2 已发生的科研治理失效

FT2DP v2.2 活跃任务记录已经确认：iter11 最后一波 4,317 帧未与此前 12,105 帧累积集完成合并；该组训练与“域内”评测实际仅消费末波 4,317 帧，即应然 16,422 帧累积数据的 26.3%，此前 12,105 帧没有参与。这证明当前缺口不是抽象的“最好有 provenance”，而是已经改变实验结论的数据谱系断链。

2.3 DeepMD-kit 3.2.0 带来的契约升级

DeepMD-kit v3.2.0 是正式稳定版，新增 DPA4/DPA4C，并扩展 pt_expt 训练、微调、change-bias、descriptor、LMDB、EMA、预训练模型注册表、.pt2 部署和 Agent Skills。DP-EVA 与上游的接口因此从少量 CLI 字符串提升为：

operation × backend × model family × artifact kind × dataset format × runtime environment

版本号合格不等于目标能力可用；必须以能力矩阵和真实行为验收替代“能 import / 能显示 help 即兼容”的弱判断。

2.4 科研目标和个人工程品味约束

  • 科学目标仍是利用预训练知识，以 2D-UQ 与 DIRECT 提高数据效率，并将候选模型交付至 Fe–C–H–O 表面、吸附和反应路径应用。
  • 治理优先级为可控、可复现、可回滚、可发布，高于再增加一个功能。
  • 验证必须断言行为和产物，不以 grep 源码字符串或仅比较文件 hash 代替功能验证；hash 只作为身份与完整性证据。
  • 本地设计文档是唯一规范源；科研运行事实不得被多处手工镜像。

3. 目标与非目标

3.1 目标

  • 让每个 workflow 具有明确、机器可读、可恢复的运行状态和失败证据。
  • 让每个数据集可以回答“来自哪里、增加了什么、是否重复、为何得到当前帧数”。
  • 让每个模型引用可以回答“是什么格式、由什么环境产生、支持哪些操作、regular/EMA 如何对应”。
  • 建立 DeepMD-kit 3.2 系列的支持区间、精确生产锁、能力矩阵和升级门禁。
  • 把候选模型评估固化为机器生成 eval-card，服务 FT2DP 训练评估与下游费托应用交接。
  • 将 PR、CPU contract、SAI GPU qualification、文档和发布检查收敛为分层而非重复的开发治理管线。
  • 保持现有工作流独立启动和底层模块复用，不以大规模重写换取表面一致性。

3.2 非目标

  • 不把 DP-EVA 重写成通用 HPC 调度器、实验追踪平台或完整训练矩阵管理系统。
  • 不在本项目复制 DeepMD-kit 内部训练器、模型实现或官方 Agent Skills。
  • 不引入 DeepMD-kit submodule/fork，不以源码镜像作为普通用户安装路径。
  • 不承诺 3.2.0 的 JAX、TF2、DPA-ADAPT、GROMACS 等全部新增能力。
  • 不在本 SPEC 内决定新的科学采样算法、论文结论或最终费托模型。
  • 不以一次全仓 DDD/mypy 重构作为治理落地前置条件。

4. 设计原则

  1. Fail closed：关键步骤失败时全局状态不得成功；完成标记只能由验证后的终态写入。
  2. Capability over version：版本用于划定支持区间，真实能力以探测和行为测试为准。
  3. Immutable evidence：历史运行与数据身份不可被无声覆盖；重新运行产生新 identity，或通过显式 resume/force 留痕。
  4. Single source of truth：代码契约在仓库，科研活动状态在外层任务跟踪，执行状态在 SAI；通过引用和 manifest 连接，不复制活状态。
  5. Layered gates：廉价检查在 PR，重型真实检查在 SAI；每层只证明自身覆盖范围。
  6. YAGNI：先治理被真实事故证明的边界；DPA-ADAPT、全后端、全自动循环等延后。
  7. Agent-readable, human-ratified：状态和证据机器可读，科学裁决仍由研究者批准。
  8. Minimal sufficient verification：门禁数量服从风险，不以堆叠检查制造虚假安全感。

5. 需求与验收信号

ID需求可观察验收信号
R1所有生成脚本采用 fail-closed 语义，完成状态不掩盖命令失败。执行一个必然失败的任务：退出码非零、状态为 failed、没有 finished marker；恢复正常命令后同一测试通过。
R2统一 canonical 运行状态全集：created、validated、submitted、running、partial、failed、finished；resume/recovery 作为事件而非新状态。Local 与模拟 Slurm 生命周期测试生成合法状态序列；非法迁移被拒绝；恢复后的终态仍规范化为 failed 或 finished。
R3每次受治理运行生成 schema-versioned run manifest。成功和失败运行均生成可校验 JSON；记录配置、版本、输入、JobID、日志、产物和状态。
R4数据集合并/清洗/采集生成 lineage manifest 和计数不变量。12,105 + 4,317 的 fixture 合并得到 16,422；遗漏来源、重复或 type-map 冲突使门禁失败。
R5模型引用显式区分 checkpoint、frozen、exportable、pretrained alias、regular 和 EMA。同一 inference 配置可枚举 regular/EMA；不兼容 backend/artifact 在提交前失败并给出原因。
R6DeepMD 支持区间、生产锁和能力状态由单一 manifest 描述。机器校验能回答指定 operation/backend/model/artifact/data/environment 的 supported 状态和证据。
R7提供显式 doctor/preflight，不在 import 时隐式探测外部命令。dpeva doctor --json 在有/无 DeepMD、版本不兼容和能力缺失环境中给出稳定 schema 与正确退出码。
R8DeepMD 3.2 CPU contract tests 进入常规 CI。真实执行 pt test/eval-desc/embed 与 pt_expt eval-desc；断言数值形状、产物和失败行为，不只断言命令字符串。
R9影响 DeepMD 能力声明的发布必须完成 SAI GPU qualification。报告记录精确 env lock、GPU、JobID、日志、fixture、regular/EMA 或 DPA4C 产物与结论。
R10候选评估由机器生成 eval-card。一条命令生成域内累积集、iter11 末波、历史域、MatPES 保持、训练成本和表面切片结果；缺项显式标记。
R11配置未知字段默认拒绝，旧扁平字段通过显式迁移层兼容。拼错字段触发校验错误；受支持旧配置输出迁移 warning 和规范化快照。
R12工作流输出默认不无声覆盖历史证据。已有 run identity 再运行默认失败或创建新 run；只有显式 resume/force 才改变既有目录并记录动作。
R13CI、本地 gate、文档说明和发布 checklist 的检查集合保持可追溯一致。机器检查比较 gate manifest 与 workflow jobs；新增对外契约同步触发 docs/recipes 检查。
R14治理规则具备依据、owner、触发痕迹和退役机制。季度审计可列出无触发规则；无证据规则被降级、合并或移除。

6. 方案比较与决策

方案内容收益主要代价裁决
A. 最小版本升级只把最低版本改为 3.2.0，更新少量示例。成本低、短期可发布。无法解决假成功、模型格式、能力差异、数据谱系和 SAI 证据；继续把兼容性建立在假设上。拒绝。
B. 能力驱动的可靠运行契约在现有 workflow 上增加 manifest、状态机、能力矩阵、分层验证和候选卡。直接覆盖已发生事故；渐进迁移；保持科学算法和产品边界。涉及公共 schema、配置迁移、CI 和 SAI 协调，需要 L3 计划。采用。
C. 全栈平台重写把训练矩阵、数据仓库、调度、应用验证全部并入 DP-EVA。单一入口、理论上自动化最高。范围和耦合急剧扩大；与外层 FT2DP/费托工作区职责冲突；中期节点前风险不可控。拒绝；未来只有重复闭环证明需要时再评估。

依赖决策：延续“外部环境依赖 + 版本约束 + 运行时能力检查”，不引入 submodule。推荐将 DeepMD 从无界强依赖迁移为受版本范围约束的 optional extra；科研生产环境以精确 lock 和资格报告冻结。

版本决策：DP-EVA 下一兼容基线为 >=3.2,<3.3；正式科研生产先锁定 3.2.0 的精确构建。3.2.x 补丁进入资格环境验证后再晋级，master/dev 永不直接生产正式结果。

兼容决策：3.1.x 降为 legacy/best-effort，不再承诺 DPA4/DPA4C；迁移期允许旧配置读取，但所有新 capability claim 只针对 3.2 系列。

8.1 Config Migration & Strict Validation

负责把受支持的旧扁平配置迁移为规范 schema，再以 extra="forbid" 验证。迁移 warning、输入 schema 版本和规范化配置快照进入 run manifest。旧键只在有明确映射和退役期限时保留。

8.2 Preflight / Doctor

显式探测 DP-EVA、DeepMD、dpdata、Torch/CUDA、CLI 子命令、backend、可见 GPU 和可选后端。输出人类文本或稳定 JSON；不在 import dpeva 时启动 subprocess。doctor 只报告环境能力，workflow preflight 进一步验证特定模型、数据和操作组合。

8.3 RunContext

在 workflow 开始时创建 run identity、目录、规范化配置和初始 manifest；为子步骤提供同一上下文。默认 run identity 由时间、短随机标识和 workflow 名组成，内容 hash 作为输入身份，不单独作为行为正确性证明。

8.4 StatusRecorder

实现合法状态迁移、事件时间、错误分类和终态写入。completion marker 是状态机的兼容输出，不是成功判据本身。Slurm 提交只进入 submitted；只有轮询/回收并验证产物后才进入 finished。

8.5 ArtifactRegistry

登记配置、日志、checkpoint、descriptor、标注数据、分析表和图。每个 artifact 有 kind、path、producer、完整性摘要和状态；敏感路径可记录逻辑 URI 或相对引用，避免把机器绝对路径固化进可发布文档。

8.6 DatasetLineage

记录父集合、变换、帧数、体系数、type map、来源清单、重复/交集摘要和输出。collect、label integration、clean 和外部 merge 均复用同一契约，不在 workflow 层复制计算逻辑。

8.7 ModelArtifactRef

统一表示本地路径、预训练 alias、regular/EMA、checkpoint/frozen/exportable、backend、head 和环境。模型 alias 在生产作业前解析到本地不可变文件并记录 checksum，禁止计算节点运行时隐式联网下载。

8.8 DeepMDAdapter

取代 DPCommandBuilder 的类级全局 backend 状态。adapter 实例根据 operation 和 capability matrix 构造命令、执行 preflight、声明预期产物并提供验证器。它仍以 CLI 为主，不包装 DeepMD 的全部功能。

8.9 EvaluationCard

将当前人工汇总升级为 schema-versioned 机器产物：记录域内累积集、iter11 末波、历史域、MatPES 保持、训练成本、表面切片和下游反馈。缺失指标不得被零值或空表掩盖，必须标记 not-run/not-applicable/failed。

  "workflow": "feature",
  "status": "finished",

  "artifacts": [{"kind": "descriptor", "path": "...", "status": "verified"}],
  "events": [{"state": "running", "at": "..."}],
  "failure": null
}

9.2 Dataset Manifest

最小字段包括 schema、dataset_id、parents、transformation、frame/system counts、type map、format、source entries、intersection summary、content identity 和验证结果。大数据集不强制逐帧 hash；允许按 set 文件摘要、Merkle/清单或抽样策略，并明确证据强度。

9.3 Model Reference

最小字段包括 artifact kind、family、backend、path/alias、resolved path、checksum、head、regular/EMA role、DeepMD version、producer run、supported operations。文件后缀只作为探测提示，不作为唯一真相。

9.4 Compatibility Manifest

以版本控制的 YAML/JSON 定义 capability key、状态、最低/最高版本、模型族、artifact、数据格式、环境类别、验证命令和最近证据。只允许 supported、experimental、unsupported、blocked-upstream 四种状态。

9.5 Schema 演进

  • 所有 schema 必须有显式版本；1.x 内向后兼容增加可选字段，破坏性变化升主版本。
  • 读旧写新：迁移器保留原始输入、记录迁移事件，不原地改写历史 manifest。
  • 历史 artifact 不因 schema 升级而失效；无法迁移时标记 legacy，而非伪造新字段。

10.3 Upstream Watch

定时任务每周读取 GitHub release、PyPI 和已登记上游 issue，生成差异报告。它可以创建维护 issue，但不得自动修改生产 lock、自动发布或宣称兼容。补丁晋级必须经过 compatibility PR 和对应资格门禁。

10.4 官方 Agent Skills

DP-EVA 文档可引用 DeepMD 官方 Skills 作为上游操作知识，不复制其内容。DP-EVA 自身只维护跨 workflow 的项目契约、preflight 和证据协议，避免两套上游操作说明漂移。

11. 开发治理模式

11.1 变更分级

级别适用变更必需产物与门禁
L1局部、可逆、不改变契约的修正。最小 diff + 相关行为检查；无需 spec/plan。
L2有界行为变更、bug、局部重构。先有能暴露缺失行为的证据；RED-GREEN；按风险 task review。
L3公共 API/schema、持久化数据、环境基线、架构或治理机制。SPEC → 用户批准 → PLAN → 分阶段实施 → 独立终审。

  -> implementation plan
  -> behavior tests + runtime evidence

  -> report/archive

11.3 PR 最小契约

  • 说明变更级别、用户可观察行为、非目标、回滚方式。
  • 若改变 CLI/config/output/status/schema/DeepMD 能力，必须同步文档、recipe 和 compatibility manifest。
  • 验证记录必须列出精确命令、结果和未覆盖边界；“单测全绿”不得外推为 GPU/Slurm 兼容。
  • 治理机制实质变化在最终合入前执行项目规定的独立治理终审；草案自审不等于 gate。

12. 状态机与错误处理

12.1 Canonical 状态机

created
  | validate success
  v
validated -------------------------> failed
  | local start          | submit
  v                      v
running <------------ submitted
  |  \                   |
  |   \ child subset     | scheduler/execution failure
  |    v                 v
  |  partial ----------> failed
  |    | explicit resume/recovery event
  |    +---------------> running
  |
  +-- execution success + artifact verification --> finished

failed -- explicit resume/recovery event --> running --> finished | failed

created、validated、submitted、running、partial、failed、finished 是唯一 canonical 状态全集。resume 与 recovery 只记录为带 attempt id 的事件；finished-after-explicit-recovery 不是新状态，恢复成功后的终态仍为 finished。

  • submitted 只证明调度器接受作业，不代表计算完成。
  • finished 同时要求执行成功、预期产物存在且验证器通过。
  • partial 表示部分子任务成功但整体验收未完成；默认 CLI 退出非零。
  • 失败运行也必须保留 manifest、日志、已产生 artifact 和 recovery hint。

12.2 错误分类

类别例子行为
CONFIG未知字段、非法 backend/head 组合提交前失败，不创建计算作业。
CAPABILITYpt_expt embed、不兼容 artifact指出 matrix 状态和支持替代路径。
ENVIRONMENTDeepMD/Torch/CUDA 缺失或版本错配doctor/preflight 失败，附环境证据。
EXECUTIONdp/ABACUS/ATST 非零退出failed；不写 finished；保留 stderr/log。
ARTIFACT命令返回 0 但 descriptor/checkpoint 缺失failed，记录 expected/observed。
DATA_INTEGRITY帧数不变量、type-map、重复冲突阻止后续训练/交接，生成审计报告。
UPSTREAMDeepMD 已知 bugblocked-upstream 或 experimental，不伪装为本项目修复。

12.3 恢复与覆盖

默认重跑创建新 run。--resume 仅恢复 schema 明确支持的未完成步骤；--force 是高可见动作，必须保存旧 manifest/产物引用和操作者理由。任何删除仍遵守项目可恢复删除纪律。

13. 测试与证据门禁

13.1 验证层次

层运行位置证明什么不证明什么
StaticPR CI格式、类型收敛区、schema、文档结构。DeepMD 数值行为、GPU、Slurm。
UnitPR CI状态机、迁移器、命令构造、manifest 校验。外部 CLI 实际可用。
CPU contractPR/定时 CI精确 DeepMD 稳定版上的真实 CLI/API 契约。V100、多 GPU、集群调度。
Local E2EPR 或 release CIworkflow 从输入到语义产物的闭环和失败传播。真实 Slurm/GPU。
SAI qualification受控 SAI目标 GPU、Torch/CUDA、Slurm、DPA4/DPA4C 真实路径。所有集群或未来版本。
Scientific acceptanceFT2DP/费托工作区候选是否满足数据与应用目标。软件对所有体系普遍正确。

13.2 DeepMD 3.2 CPU Contract 初始集合

  • dp --version 与 doctor schema。
  • dp --pt show 的 model family/head/type-map 探测。
  • PT test、eval-desc、embed 的真实小 fixture。
  • pt_expt DPA4C eval-desc；pt_expt embed 在提交前被明确拒绝。
  • regular/EMA 引用与结果隔离。
  • NPY/mixed/LMDB 的计数和短路径语义对照。
  • 外部命令失败、返回 0 但产物缺失、部分子任务失败三类负向行为。

13.3 测试纪律

  • 行为测试必须执行目标路径并检查退出码、状态和语义产物。
  • 命令字符串单测可以保留为局部构造检查，但不能承担兼容性验收。
  • 数值对照使用物理上有意义的容差；不得以 fixture 全文件 hash 代替数值语义。
  • hash 用于证明 artifact 身份、传输完整性和 lineage，不用于证明算法正确。
  • skip 必须带原因和 owner；release blocker 不得通过 skip 变绿。

13.4 Gate Manifest

使用单一 gate manifest 描述 lint、unit、coverage、CPU contract、integration、docs、audit 和 qualification 的命令与适用触发条件。本地 gate.sh 与 GitHub Actions 从同一清单派生或由一致性测试约束，防止“本地全绿”和“CI 全绿”语义分叉。

14. 文档与决策治理

14.1 文档层级

  • AGENTS.md：仅保留最小入口、事实源和关键门禁指针。
  • developer-guide：承接稳定开发契约，不承载活科研进度。
  • reference：schema、CLI、配置和 capability matrix 的权威解释。
  • spec/plan/report：分别保存决策、实施和验收证据；完成版本后归档。
  • 外层 task/checkpoint：保存 FT2DP 活动状态与研究者 ruling。

14.2 Traceability

每项公共能力都应能从 feature/requirement 链接到代码、测试、recipe、文档、owner 和最近资格证据。矩阵自动检查路径存在与更新时间，但不通过源代码字符串匹配推断功能正确。

14.3 Ruling 纪律

执行计划中的必要裁决记录“决定—理由—错了的代价”，并回写对应 plan/report。Ruling 不是绕过验收的豁免；改变公共契约时必须回到 spec/plan。

14.4 Use-it-or-lose-it

治理规则、检查和文档每季度检查触发痕迹。长期无命中、无事故依据或与其他门禁重复的规则应合并、降级或移除，避免治理管线成为只增不减的负担。

15. 迁移、发布与回滚

15.1 Phase 0：可靠性止血

  • 修复脚本和多进程失败传播，完成标记改由产物验证后的状态机写入。
  • 逐一复现并把当前 3 个 integration failures 归类为产品缺陷、fixture/测试基础设施缺陷或 harness/环境假象；只有确认的产品失效才转化为 R1/R2 负向回归，测试基础设施问题在原测试层修复并留证。
  • 冻结新 capability claim，直到假成功路径关闭。

出口：R1、R2 的负向测试通过；任何失败任务不再被报告为 finished；3 个既有 integration failures 均有可复现证据、归类结论与对应处置，未激活环境等 harness 假象不被误记为产品根因。

15.2 Phase 1：契约内核

  • 实现 schema 包、RunContext、StatusRecorder、doctor 和 artifact validators。
  • 先接入 feature/infer，再接入 train/collect/label/clean/explore，避免一次性横切全仓。
  • 配置切换为“先迁移、后严格验证”。

出口：

  • R3：至少 feature 与 infer 的成功、失败、partial 路径均产出合规 manifest。
  • R7：dpeva doctor --json 在 DeepMD 可用、缺失、版本或能力不兼容三类环境中返回稳定 schema、正确状态和退出码；import dpeva 不再启动外部探测。
  • R11：未知/拼错字段在提交前失败；受支持旧配置完成“保留原文—显式迁移 warning—输出规范化快照”的闭环。
  • R12：同一 run identity 的默认重跑不得覆盖既有证据；新 run、显式 resume 与显式 force 均产生可区分事件和产物记录。

15.3 Phase 2A：科研谱系与候选卡

  • 落地 dataset lineage 和 merge invariants。
  • 落地 ModelArtifactRef、regular/EMA 和 eval-card。
  • 将 FT2DP 四件套与表面切片接入候选包。

出口：用 12,105 + 4,317 的回归场景证明漏合并会阻断；一条命令生成完整候选卡。

15.4 Phase 2B：DeepMD 3.2 Compatibility Lane

  • 依赖分层、stable lock、capability manifest 和 CPU contract CI。
  • 完成 SAI V100 DPA4/DPA4C 资格验证，更新旧 dev67/旧路径文档。
  • 按证据把能力从 experimental 晋级 supported。

出口：DeepMD 3.2 兼容报告、env lock、JobID、日志和能力矩阵一致。Phase 2A 与 2B 在 Phase 1 的 schema 和状态契约冻结后可并行实施，分别由 Scientific Owner 与 Compatibility Owner 负责。

15.5 Phase 3：受控科学扩展

  • DPA4 五档基座 alias、LMDB、.pt2、DPA4C 采样引擎。
  • Energy-LLPR 统计验证；Force-DPOSE 保持实验性直至稳定接口和 GPU fixture 就绪。
  • 只有人工闭环稳定重复至少两轮后，才设计自动 cycle runner。

15.6 兼容与回滚

  • 旧配置通过迁移层读取一个明确退役周期；原始配置保留。
  • 旧输出目录仍可解析为 legacy run，但不伪造新 manifest 的未知字段。
  • 新 schema 先 opt-in 试点，稳定后成为默认；必要时可切回 legacy execution adapter。
  • 生产 DeepMD 升级通过独立环境晋级；回滚只切换环境锁和 capability evidence，不覆盖历史结果。
  • 任何批量迁移先生成 dry-run 报告和备份引用，不删除科研资产。

15.7 发布语义

Phase 0 可作为 0.8.x 可靠性修复；schema、strict config、依赖分层和新模型引用属于显著公共契约变化，建议进入 0.9.0。不得在未完成资格验证前将 experimental 能力写入 release notes 为“正式支持”。

15.8 实施计划分解

本 SPEC 固化共同架构，但范围不应塞入一个实施计划。批准后至少拆成以下可独立验收、按顺序或并行执行的 plans：

  1. Plan A — Reliable Execution Kernel：R1、R2、失败传播，以及现有 integration failures 的逐项复现、归类和对应修复。实施计划
  2. Plan B — Run Contract & Strict Config：R3、R7、R11、R12 和 schema/migration 基座。实施计划
  3. Plan C — Dataset Lineage & Eval Card：R4、R5、R10，对接 FT2DP 候选包。实施计划
  4. Plan D — DeepMD 3.2 Compatibility Lane：R6、R8、R9、依赖分层、CPU/SAI 资格验证。实施计划
  5. Plan E — Governance Alignment：R13、R14、gate manifest、traceability 和文档收口。实施计划

Plan A 是所有后续计划的硬依赖；Plan B 完成 schema 最小基座后，Plan C 与 Plan D 可并行；Plan E 随各计划增量落地并在 0.9.0 发布前最终收口。

15.9 轻治理实施约束

  • 当前执行批次只覆盖 Phase 0、Phase 1、Phase 2A、Phase 2B 与治理收口；Phase 3 必须由新的科学需求和独立批准启动。
  • Plan A、Plan B 分别设置停止点；只要可靠性止血或 feature/infer 试点尚未给出正收益证据，就不得横向接入其余 workflow。
  • schema 只保留已被 R1–R12 消费的字段；不得为推测中的平台化、全自动循环或未知后端预留抽象层。
  • 新增 gate 必须替代重复检查或带来独有失败检出能力；Plan E 不以增加 gate 数量作为完成信号。
