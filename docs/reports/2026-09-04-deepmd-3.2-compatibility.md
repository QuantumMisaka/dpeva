# DeepMD-kit 3.2 Compatibility Qualification

## Decision

This report records the evidence available for the DeepMD-kit 3.2
compatibility lane. It is a bounded engineering qualification record, not a
scientific performance result. Four explicitly implemented DPA4 PT
capabilities are promoted to `supported` from complete CPU and SAI evidence:
the three npy capabilities plus the LMDB `test` path. The DPA4C result remains
experimental because the tested artifact is not a verified DPA4C
model-family artifact. All other capabilities remain deliberately bounded by
their current status.

The compatibility manifest and this report must be updated together. A
DeepMD version number alone is never sufficient for promotion.

## Manifest status distribution

The current 21-record manifest (`src/dpeva/compatibility/deepmd-3.2.json`)
has the following explicit distribution:

| Status | Records |
|---|---:|
| `supported` | 4 |
| `experimental` | 9 |
| `unsupported` | 4 |
| `blocked-upstream` | 4 |

LMDB `test` is promoted by the exact CPU contract (`1893534`) and the SAI
npy↔LMDB A/B qualification (`1893546`). LMDB `train` now has a finished CPU
contract but remains experimental because the A/B qualification covers
`dp test`, not a production training run. LMDB `fine-tune` remains planned;
`eval-desc` and `embed` are blocked upstream by
[DeepMD-kit issue #6034](https://github.com/deepmodeling/deepmd-kit/issues/6034).

The two CPU non-PBC DPA4C records (`eval-desc` and `inference`) remain
`blocked-upstream` pending [DeepMD-kit issue #6002](https://github.com/deepmodeling/deepmd-kit/issues/6002)
and a fixed-version non-PBC contract. Neither record is promoted by this
report.

## CPU contract evidence

The SAI CPU-contract job `1128442` ran in the exact `dpeva-dpa4-320`
environment and produced **11 passed / 0 skipped**. Three promotion-grade CPU
attestations are retained under `docs/reports/evidence/deepmd-3.2/`; the
single selected model contract covers the declared `regular` model path.
The LMDB CPU-contract job `1893534` ran in the same exact environment against
a protected periodic fixture and a generated `deepmd/lmdb` copy, producing
**8 passed / 0 skipped**. Its `pt-test-lmdb` and `pt-train-lmdb` attestations
are retained under
`docs/reports/evidence/deepmd-3.2/lmdb-cpu-job-1893534-attestations/`. The
LMDB test contract also exercises the DP-EVA frame-index parser on the real
`dp test -d` detail rows. These are contract results, not scientific accuracy
or general model-family claims.

The exact SAI runtime retains `dpdata 1.0.2`; the LMDB fixture used by the
CPU contract was generated once outside that runtime with `dpdata 1.1.0` and
copied into the job. The CI contract lane generates the equivalent fixture
in-test under `dpdata>=1.1`. Thus the CPU job proves the exact DeepMD
reader/CLI and DP-EVA parser path; the dpdata writer is separately exercised
in the `ft2dp-post` 1.1 lane and by the CI fixture generation step.

The CI contract lane is intentionally stricter: it downloads a protected
fixture bundle, verifies the configured URL and SHA-256, sets
`DPEVA_DEEPMD_CONTRACT_REQUIRED=1`, and rejects missing fixtures or skipped
cases. The required command is:

```text
pytest -m deepmd_contract tests/contract/deepmd -q
```

The local fixture skips cannot be substituted for that CI-required positive
fixture evidence.

artifact as the regular DPA4 checkpoint. That equality, together with the

The ordinary development environment remained separate from the exact

The LMDB A/B job `1893546` ran on `4V100` with the exact same environment and

| Metric | npy | lmdb | Relative difference |
|---|---:|---:|---:|
| Energy MAE/atom | 1.836583e+03 | 1.836583e+03 | 0 |
| Force MAE | 1.696743e-01 | 1.696743e-01 | 0 |
| Virial MAE/atom | 8.897196e-02 | 8.897196e-02 | 0 |

The LMDB detail rows were attributed to 2,604 frames via the frame index; the
external LMDB snapshot exposes 841 composition-group identities, not the
964 npy directory identities. This is a storage-identity boundary, not a
metric difference. The raw A/B result and logs remain in the immutable SAI
evidence directory; the sanitized public summary is
`docs/reports/evidence/deepmd-3.2/sai-lmdb-ab-job-1893546-public.json`. The
one-case SAI promotion attestation is
`docs/reports/evidence/deepmd-3.2/sai-lmdb-ab-job-1893546-attestation.json`.

The real training execution A/B job `1893783` ran the same 16,485-frame
training corpus as `deepmd/npy/mixed` and `deepmd/lmdb` for 200 steps, with
the same 2,604-frame npy validation set and seed. Both commands returned zero
and wrote step-200 checkpoints. Steady-state step-100/200 wall times were
close: mixed `34.98/37.71 s`, lmdb `36.46/35.96 s`; first-batch compilation
time is not comparable. The 200-step lcurve is stochastic and is deliberately
not treated as a bitwise format-equivalence gate: the force-validation MAE
differed by 13.6% in this run. The run qualifies the real training execution
path, not training-metric equivalence. `train + deepmd/lmdb` therefore remains
experimental. The sanitized summary is
`docs/reports/evidence/deepmd-3.2/sai-lmdb-train-ab-job-1893783-public.json`;
raw logs, lcurves, checkpoints, and `train_ab_result.json` remain on SAI.

## Promotion rule and conclusion

Promotion requires a producer-issued per-capability attestation (or a
qualification aggregate containing such attestations) whose exact manifest
key, verification command, `DeePMD-kit v3.2.0`, and finished/zero-return-code
fields match. Repository-local references must resolve to JSON files; report
anchors and raw command records are insufficient. A capability whose
`required_evidence` includes `sai-v100-qualification` additionally requires a
numeric JobID and V100 identity, and its complete `sai_verification_cases`
set must be present exactly once. Qualification aggregates are bound to the
launch input SHA and its manifest-derived attestation specs; stale specs fail
collection instead of being reinterpreted against the current manifest.
Unsupported and blocked-upstream records cannot be promoted by an
environment/version check.

The collector treats the verified `environment/gpu.json` value as the sole
GPU identity. An optional CLI GPU value is only an expected diagnostic and
must match the recorded value after whitespace normalization; mismatches,
non-numeric or inconsistent JobIDs, empty bound specs, and any per-spec
attestation construction anomaly produce `status=failed` with zero finished
attestations.

The present evidence satisfies the promotion gate for exactly four records:
DPA4 `pt test`, `pt eval-desc`, `pt embed`, and `test + deepmd/lmdb`. Their
manifest entries point to the corresponding CPU attestation and the matching
SAI aggregate. Keep the periodic DPA4C `pt-expt eval-desc` record experimental
with no promotion reference: `--pt-expt` command success alone does not
establish the DPA4C model family. A future promotion requires a genuine DPA4C
artifact and family preflight. Keep LMDB `train` and `fine-tune` experimental
until real training evidence exists, the four policy `unsupported` records
unchanged, both non-PBC records blocked by issue #6002, and the two LMDB CLI
exporters blocked by issue #6034.

## Retry and ownership boundary

The successful SAI qualification supersedes the earlier cancelled diagnostic
attempt (`1126627`); that earlier attempt remains historical evidence only.
Future promotions require a new bounded job, complete immutable
`qualification.json`, and `--require-complete` before any manifest edit.
